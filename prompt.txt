# IMPLEMENTATION PROMPT
# Experiment 6A — Closed-Loop State-Conditioned Velocity Observer
# IDR-Nav / IO-VNBD

Implement Experiment 6A as a controlled research experiment for the IDR-Nav
system.

The objective is NOT merely to improve velocity MAE.

The objective is to determine whether a state-conditioned AI velocity observer
can improve the complete smartphone INS dead-reckoning system under GNSS
outage, particularly on the held-out Driver E vehicle.

============================================================
1. PROBLEM CONTEXT — DO NOT LOSE THE ACTUAL SIH OBJECTIVE
============================================================

The target system must ultimately satisfy the following requirements:

- No OBD-II / vehicle speedometer connection.
- AI/ML-based forward velocity estimation from accelerometer + gyroscope.
- Robustness to vibration, potholes, engine harmonics and phone mounting effects.
- GNSS + INS fusion.

- Offline road-network map matching.
- Seamless GNSS → INS transition during outage.
- Seamless INS → GNSS recovery.

Experiment 6A addresses specifically the AI velocity-observer component.

Do NOT redesign the entire navigation stack during this experiment.

The purpose is to test whether temporal state conditioning solves the verified
high-speed observability problem.

============================================================
2. FORENSIC FINDINGS MOTIVATING EXPERIMENT 6A
============================================================

Experiment 5 forensic analysis established:

1. An isolated 4.8 s IMU window contains insufficient reliable information to
   distinguish absolute highway speeds on unseen vehicles.

2. Driver E exhibits a substantially different chassis / phone-mount vibration
   transfer function from the training vehicle.

3. 95.4% of all 80+ km/h training data originates from Driver A's vehicle.

4. The current model therefore partially learns vehicle-dependent vibration
   signatures as speed.

5. The uncertainty head is overconfident on Driver E at high speeds.

6. An accelerometer fundamentally provides acceleration rather than absolute
   velocity:

       v[t] = v[t-1] + integral(a_forward dt)

Therefore Experiment 6A changes the learning problem from:

       "infer absolute speed from a 4.8 s vibration snapshot"

to:

       "maintain and correct an existing velocity state using local IMU
        kinematics and physical velocity anchors."

============================================================
3. CORE STATE-CONDITIONED FORMULATION
============================================================

At timestep t:

    v_anchor[t] = observer's previous estimated forward velocity

    Δv_hat[t] = Network(IMU_window[t], v_anchor[t])

    v_raw[t] = v_anchor[t] + Δv_hat[t]

    v_hat[t] = max(0, v_raw[t])

The model therefore learns the local velocity change while the observer state
maintains absolute velocity information across time.

Do NOT turn the model into a simple absolute-speed regressor with an extra
scalar feature.

The central hypothesis is that temporal state provides information that is
physically unavailable in an isolated IMU window.

============================================================
4. ZERO GROUND-TRUTH VELOCITY LEAKAGE
============================================================

THIS IS A HARD REQUIREMENT.

During training:

    NEVER provide v_gt[t-1] as v_anchor[t].

Ground-truth velocity may ONLY be used to calculate losses and evaluation
metrics.

The recursive state must come from the model's own previous prediction:

    v_anchor[t] = detach(v_hat[t-1])

This must be true during training, validation and testing.

Do not use teacher forcing.

Do not alternate between GT state and predicted state.

Do not silently reset the state to GT velocity.

The implementation should make it straightforward to audit that no GT velocity
enters the model's state input.

============================================================
5. TRAINING STRATEGY — TRUNCATED CLOSED LOOP
============================================================

Use chronological sequences from individual continuous drives.

Sequence length:

    L = 32 timesteps

Dataset sampling frequency:

    10 Hz
    Δt = 0.1 s

Do NOT silently change the temporal resolution to 0.2 s.

Each sequence should therefore represent approximately:

    32 × 0.1 = 3.2 seconds

of recursive observer operation.

Never cross drive boundaries.

Training tensor:

    X: (B, L, 18, 48)

Targets:

    y: (B, L)

Each element contains the existing 48-sample / 4.8-second IMU context.

At sequence start:

    v_state = 0

Then:

    for t in range(L):

        out = model(
            X[:, t],
            v_anchor=v_state
        )

        v_pred = out["mu_v"]

        store(v_pred)

        v_state = v_pred.detach()

The detach is intentional for the initial experiment.

This is truncated closed-loop training rather than full backpropagation
through arbitrarily long drives.

However, validation and final evaluation MUST run continuously without
artificial sequence resets.

============================================================
6. IMPORTANT — SEQUENCE START STATE
============================================================

Training sequences may begin with:

    v_state = 0

because this provides a conservative, leakage-free initialization.

However, do not let the model become dependent on every sequence starting
from zero.

During validation and final evaluation:

    initialize once at the beginning of the drive

and then maintain state continuously.

Do NOT reset v_state every 32 timesteps.

The final evaluation must represent a continuously operating navigation
observer.

Also report convergence from:

    v0 = 0 km/h

because this is the production-safe initialization.

============================================================
8. MODEL ARCHITECTURE
============================================================

Modify:

    ml/src/model.py

Preserve the existing:

- ConvNeXt-1D backbone
- Temporal Multi-Head Attention
- 18-channel physics representation
- Channel 15 turn gating
- BatchNorm1d(18)
- existing output heads wherever possible

Add a small state-conditioning pathway:

    state_proj =
        Linear(1 → 32)
        GELU
        Linear(32 → 32)

Conceptually:

    z_imu = existing global pooled representation

    e_state = state_proj(v_anchor_norm)

    z = concatenate(z_imu, e_state)

If the existing pooled representation is 128-dimensional:

    z = 160-dimensional

The velocity head should predict:

    Δv_hat

and uncertainty:

    sigma_v

Then reconstruct:

    v_raw = v_anchor + Δv_hat

    mu_v = max(0, v_raw)

Do NOT use ReLU on the residual itself.

Do NOT use:

    ReLU(Δv)

because negative acceleration/deceleration is physically required.

The non-negativity constraint belongs on the final velocity estimate.

If a hard clamp is implemented, verify that it does not create undesirable
gradient behavior near zero.

============================================================
14. CORRECT EKF COORDINATE MAPPING
============================================================

The previous evaluation scripts contained a confirmed variable-shadowing bug.

The correct mapping from align_imu_to_vehicle_frame() is:

    aligned_imu[0] = lateral acceleration
    aligned_imu[1] = forward acceleration
    aligned_imu[2] = vertical acceleration

Therefore the EKF must use:

    ax_b = lat_acc[k]
    ay_b = fwd_acc[k]
    az_b = vert_acc[k]

Do NOT use:

    ax_b = fwd_acc[k]

The correction applies to:

    ml/src/task3_indistribution_evaluation.py

and:

    ml/src/evaluate_full_pipeline.py

IMPORTANT:

Do NOT modify production Flutter EKF code merely as part of this experiment.

First verify whether the production implementation already follows the correct
coordinate convention.
